New Employee Joins the Warehouse

HR/Admin is informed a new person needs GiNi access

❓ What kind of employee is this?

This single decision determines every Role, Role Group and Profile choice that follows

↓branches into 4 paths

Step 2 — Role IDs → Role Group → Profile Mapping (per employee type)

📦 Picker / Floor Worker

1. Role IDs (Android)Normal_Pick, Short_Product, Skip, Cut_Product — each is ONE voice-command permission
↓
2. Role Group"Picker-Standard" bundles those Role IDs. Cockpit access = No Access / View-own-performance only
↓
3. Profile — Grid 1Create Profile "PICKER-ZONE-A"
4. Profile — Grid 2 (Functions)Picking YES Putaway NO Cycle Count NO
5. Profile — Grid 3 (Work Types)Normal Pick YES Short Product YES Override NO

📊 Supervisor

1. Role IDs (Cockpit)Can_View_Dashboard, Can_View_Reports, Can_Manage_Assignments, Can_Reject_Assignment
↓
2. Role Group"Supervisor-Standard" — Dashboards = Full, Picking = Full, Master Data = View, User Mgmt = No Access
↓
3. Profile MappingUsually N/A — supervisors work in Cockpit, not on the Android device
Exception: if they also need floor Override rights, a limited Android profile is mapped too

👤 Warehouse Admin

1. Role IDs (Cockpit)Can_Edit_Users, Can_Edit_Roles, Can_Edit_MasterData, Can_View_All
↓
2. Role Group"Warehouse-Admin-Full" — every module set to Full Access (User Mgmt, Master Data, Picking, Reports)
↓
3. Profile MappingN/A — admins don't operate the Android scanner

🔧 IT / BA

1. Role IDs (Cockpit)Can_View_Logs, Can_Release_Session, Can_Upload_License
↓
2. Role Group"IT-BA-System" — System = Full, Licensing = Full, everything else = View or No Access
↓
3. Profile MappingN/A — this role is Cockpit/back-end only
Remember the hierarchy: Role ID = ONE permission (one key) → Role Group = a bundle of Role IDs (a keychain) → the Role Group is what actually gets assigned to a User. You never assign individual Role IDs to a person directly — always through a Role Group. Profile Mapping is a separate, parallel system that only matters for people who use the Android device (mainly Pickers) — it controls voice commands, not Cockpit pages.
all four paths now converge

Step 3 — Create the User in User Management

➕

Admin → User Management → Add User

Fill: Username, Full Name, Email, Status = Active, Client ID

↓
🔗

Assign the Role Group built in Step 2

Picker → "Picker-Standard"  |  Supervisor → "Supervisor-Standard"  |  Admin → "Warehouse-Admin-Full"  |  IT/BA → "IT-BA-System"

↓
📱

Assign Profile ID (Android users only) + Default Page

e.g. Profile "PICKER-ZONE-A" for a picker; Default Page = the screen that opens after login

↓
✅

Save → User appears in Active Users

The account now exists but has never logged in yet

↓

Step 4 — First Login: Everything Gets Checked

🔐

Enter Client ID + Username + Password

App sends a POST request to /api/Global

↓
🗄️

Server validates credentials → Token generated → Session created

Proves this login is genuine, like a wristband for this session

↓
☰

GetHamburger() API is called

Looks up the user's Role Group → checks every Role inside it (Full / View / Custom / No Access)

↓
🧭

Menu is built dynamically + Default Page opens

Only the pages this Role Group allows are shown — nothing is hardcoded

↓the same login process, four very different results

Step 5 — What Each Employee Type Actually Sees

📦 Picker sees:

Android app only. Hears "Go to Bin…", can say "Confirmed", "Short Product", "Skip". Saying "Override" is rejected — not in their Profile.

📊 Supervisor sees:

Cockpit Dashboards + Picking modules with full control. Master Data is view-only. User Management does not appear in their hamburger menu at all.

👤 Warehouse Admin sees:

Every Cockpit module: User Management, Roles, Master Data, Picking, Dashboards — all with full Add/Edit/Delete rights.

🔧 IT/BA sees:

System (GiNi Logs) and Licensing (Session Management) modules. Other business modules are view-only or hidden.

What Happens Later — 3 Lifecycle Flows

🔄 Employee's Role Changes

Admin opens User Management → selects user → Edit → assigns a different Role Group (or Profile)
↓
Save. Nothing happens to their current session
↓
Next login, GetHamburger() re-runs automatically and builds the new menu — no app update needed

🚪 Employee Leaves

Admin → User Management → select user → Delete → Confirm
↓
User moves to the Inactive tab — NOT permanently deleted
↓
All historical picks/assignments/performance data is preserved for audit

♻️ Employee Rejoins

Admin → Inactive Users tab → select the user → Edit
↓
Change Status from Inactive → Active
↓
Save → user moves back to Active Users, same Role Group/Profile as before (can be updated if their situation changed)
Exam angle to remember: Cockpit Roles control pages (Full / View / Custom / No Access). Android Roles control voice commands (Enabled / Disabled / Custom). Role Groups are the only thing ever assigned to a User directly. Profile Mapping (Grid 1 → Grid 2 → Grid 3: Profile → Functions → Work Types) is the completely separate system that shapes the Android experience, used mainly for Pickers/Putaway staff.
